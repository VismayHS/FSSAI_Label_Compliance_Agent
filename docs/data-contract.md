# Data contract: `POST /v1/runs` (v1.0)

Owner: Vihaan · Requirements: F1 (published data contract), F2 and D1 (validation at the ingestion boundary,
quarantine) · Enforced by `fssai_gate.gate:RequestGate` (`libs/gate`) · Machine-readable form:
[`data-contract.schema.json`](data-contract.schema.json) (JSON Schema 2020-12, generated by
`eval/tools/export_schema.py` from the same code the gate runs, so the two cannot drift apart).

This contract binds both sides. A caller that sends a request meeting it gets a run. A request that does not
meet it is **rejected at the boundary, stored in quarantine with every error found, and never reaches an
agent** (no run row, no queue job). Everything downstream of the gate may assume valid data.

**What the gate does not check.** It checks that a request is *well formed*. It never decides
compliance. A label with no allergen statement, no licence number or no veg mark is a valid request: those
are exactly the things the agents check and report as `unmet`. A category the corpus does not cover is also
valid; that run escalates to `regulatory-review` (F7).

## 1. Order of checks at the gate

| # | Stage | On failure | Quarantined? |
|---|---|---|---|
| 0 | API: `X-Client-Id` header, body size (`API_MAX_REQUEST_BYTES`) | `400` / `413` | no (never reached the gate) |
| 1 | Per-client rate limit (token bucket, D7) | `429 {retry_after_s}` + `Retry-After` | **no**: the request was not malformed, and no validation work is spent on it |
| 2 | JSON object; unknown fields; schema and types | `422` | yes |
| 3 | `schema_version`; ranges; lengths; formats; permitted values | `422` | yes |
| 4 | Category id format | `422` | yes |
| 5 | Cross-field rules XF-01 to XF-10 (need typed values, so they run whenever stage 2 passed) | `422` | yes |

Stages 2 to 4 all run, whatever fails first, so a caller gets **every** error in one response, not one per
attempt. A non-JSON body is not dropped by the framework: the API wraps it and the gate quarantines it with
code `json_invalid`.

## 2. Fields

All numbers are JSON numbers: `12` and `12.0` are fine, but the string `"12"` is rejected (`type`), and so are `NaN`
and `Infinity` (`range`; some JSON encoders emit them, and no comparison with NaN can fail). Nutrition values are **per 100 g or per 100 ml as stated by `basis`**, which is
how FSS-LD-2020 5(3)(b) asks for them on the label ("Nutritional Information per 100g or 100ml"). The bounds
below are sanity bounds that catch unit mistakes and impossible values. They are **not regulatory thresholds**.
Where a bound comes from physics or from the regulation, the "Why" column says so.

### Top level

| Field | Type | Required | Range / permitted values | Why |
|---|---|---|---|---|
| `schema_version` | string | no (default `"1.0"`) | `1.<minor>` | Additive changes keep major 1 (§6). |
| `client_reference` | string | no | ≤ 128 chars | The caller's own id; echoed in runs, never interpreted. |
| `declared_category` | string | **yes** | lower-case id, `[a-z0-9]` words joined by `-`, 2–64 chars | See §3. |
| `package` | object | **yes** | §2.1 | |
| `label` | object | **yes** | §2.2 | |
| `nutrition` | object | **yes** | §2.3 | |

Unknown fields are rejected (`unknown_field`) at every level except `nutrition.other`. A misspelt
`protien_g` is otherwise silently dropped, and the label would be checked without the value its author meant
to send.

### 2.1 `package`

| Field | Type | Unit | Required | Range / permitted values | Why |
|---|---|---|---|---|---|
| `net_quantity` | number | `net_quantity_unit` | **yes** | > 0; ≤ 100 000 for `g`/`ml`, ≤ 100 for `kg`/`l` | 100 kg or l is beyond any retail pack. "500 kg" almost always means 500 g. |
| `net_quantity_unit` | string | | **yes** | `g`, `kg`, `ml`, `l` | |
| `principal_display_panel_cm2` | number | cm² | **yes** | > 0, ≤ 10 000 | 1 m². The veg-mark size table (FSS-LD-2020 5(4)(c)) is keyed on this area. |
| `total_surface_area_cm2` | number | cm² | no | > 0, ≤ 50 000 | Decides the small-pack exemption (FSS-LD-2020 8(1), "not more than 100 square centimetres"). Send it whenever it is known. |
| `pack_type` | string | | no | `single`, `multipack`, `institutional`, `non-retail` | `non-retail` packs have their own list (FSS-LD-2020 10). |

### 2.2 `label`

Every free-text field is **untrusted input** (L4). The gate only bounds its length; the guardrails screen its
content.

| Field | Type | Required | Range / permitted values | Notes |
|---|---|---|---|---|
| `product_name` | string | **yes** | 1–200 chars, not blank | |
| `brand_name` | string | no | ≤ 200 chars | |
| `front_of_pack_text` | string | no (default `""`) | ≤ 4 000 chars | Matches `GUARDRAIL_MAX_FIELD_CHARS`. |
| `claims` | array of string | no (default `[]`) | ≤ 20 items, each 1–200 chars, not blank | Each claim **exactly as printed**, e.g. `"Source of protein"`. XF-10 applies. |
| `ingredients` | string | no (default `""`) | ≤ 4 000 chars | Empty means "no list printed", which is a finding, not a reject. |
| `allergen_statement` | string | no | ≤ 1 000 chars | Absent means "none printed". |
| `veg_status` | string | no (default `not_declared`) | `veg`, `non_veg`, `not_declared` | The mark printed on the pack (FSS-LD-2020 5(4)). |
| `fssai_licence_number` | string | no | 14 digits, spaces allowed | FSS-LD-2020 5(7)(a) shows the format as "Lic. No. XXXXXXXXXXXXXX" (14 places). Leave it out if none is printed. |
| `manufacturer_name_address` | string | no | ≤ 1 000 chars | |
| `date_marking` | string | no | ≤ 200 chars | As printed. |
| `batch_or_lot` | string | no | ≤ 100 chars | |
| `other_text` | string | no | ≤ 4 000 chars | Anything else printed on the pack. |

### 2.3 `nutrition`

| Field | Type | Unit (per 100 g/ml) | Required | Range | Why |
|---|---|---|---|---|---|
| `basis` | string | | **yes** | `per_100g`, `per_100ml` | Solids vs liquids also selects the claim condition (FSS-AC-2018 Schedule I "for solids" / "for liquids"). |
| `serving_size` | number | `serving_unit` | no | > 0, ≤ 1 000 | XF-02, XF-03. |
| `serving_unit` | string | | no | `g`, `ml` | XF-02, XF-03. |
| `energy_kcal` | number | kcal | **yes** | 0–900 | Pure fat at 9 kcal/g (FSS-LD-2020 5(3)(e)(i)) gives 900 kcal per 100 g; nothing exceeds it. XF-08. |
| `protein_g` | number | g | **yes** | 0–100 | Cannot exceed the 100 g it is declared for. |
| `carbohydrate_g` | number | g | **yes** | 0–100 | |
| `total_sugars_g` | number | g | **yes** | 0–100 | XF-05. |
| `added_sugars_g` | number | g | no | 0–100 | XF-04. |
| `total_fat_g` | number | g | **yes** | 0–100 | XF-06. |
| `saturated_fat_g` | number | g | no | 0–100 | XF-06. |
| `trans_fat_g` | number | g | no | 0–100 | XF-06. |
| `sodium_mg` | number | mg | no | 0–40 000 | Sodium is about 39 % of salt by mass (a chemistry fact), so even 100 g of salt stays under 40 000 mg. |
| `other` | object of number | per key | no (default `{}`) | each ≥ 0; ≤ 100 for `_g`, 100 000 for `_mg`, 10⁸ for `_mcg`, 900 for `_kcal` | Further nutrients. Each key is `snake_case` and **ends in its unit**: `dietary_fibre_g`, `cholesterol_mg`, `iron_mg`, `vitamin_d_mcg`. Fibre claims are checked against `dietary_fibre_g`. |

## 3. Categories: supported and unsupported

The corpus covers one category, **`breakfast-cereals`** (decision 001; `CORPUS_CATEGORIES` in `.env`).

| `declared_category` | Gate | What happens |
|---|---|---|
| `breakfast-cereals` | accepted | Full check. |
| Any other well-formed id (`protein-powder`, `alcoholic-beverage`, `other`, ...) | **accepted** | The classifier marks it out of scope, and the run is routed to `regulatory-review` with "category outside corpus" and no research (F7, demo #5). Use `other` if the category is unknown. |
| Malformed (`Breakfast Cereals`, `x`, `""`) | rejected, code `category` | |

Unsupported categories are accepted rather than rejected on purpose. F7 requires the system to *escalate* an
out-of-corpus product, and a reject would hide the product from the reviewer queue, the trace and the
evaluation. The classifier also cross-checks the declared category against the label. A "cereal" whose
first ingredient is a protein isolate and that carries supplement wording escalates, because claims for
health supplements are governed by another regulation (FSS-AC-2018 Schedule I, Note 1).

## 4. Cross-field rules

Each rule's id is the `code` of the `FieldError` it produces.

| Id | Rule | Example violation | Why |
|---|---|---|---|
| XF-01 | A `per_100ml` panel needs a net quantity in `ml` or `l`. | `basis: per_100ml`, `net_quantity_unit: g` | A liquid basis on a pack sold by weight means one of the two is wrong, and the claim condition differs by basis. |
| XF-02 | `serving_size` and `serving_unit` are given together or not at all. | `serving_size: 30`, no unit | A size without a unit is unusable. |
| XF-03 | `serving_unit` is `g` for `per_100g` and `ml` for `per_100ml`. | `per_100g` with `serving_unit: ml` | Mixed units make per-serve values incomparable. |
| XF-04 | `added_sugars_g ≤ total_sugars_g`. | added 10, total 9 | Added sugars are part of total sugars. |
| XF-05 | `total_sugars_g ≤ carbohydrate_g`. | sugars 80, carbohydrate 72 | Sugars are part of carbohydrate. |
| XF-06 | `saturated_fat_g + trans_fat_g ≤ total_fat_g`. | saturated 1.2 + trans 5.5 > fat 6 | Both are fractions of total fat. |
| XF-07 | On a `per_100g` panel, `protein_g + carbohydrate_g + total_fat_g ≤ 100` (+1 g rounding). | 40 + 60 + 10 = 110 | Mass balance; each figure is rounded, hence 1 g of slack. Not applied to `per_100ml`, where density is unknown. |
| XF-08 | `energy_kcal` within ±20 % (at least ±10 kcal) of `4·protein + 4·carbohydrate + 9·fat`. | 300 kcal declared, 382 computed | See below. |
| XF-09 | `principal_display_panel_cm2 ≤ total_surface_area_cm2` when both are given. | panel 180, surface 100 | The panel is part of the surface. |
| XF-10 | A claim about a nutrient that is optional on the panel needs that nutrient declared. | `"Low sodium"` with no `sodium_mg`; `"High in fibre"` with no `other.dietary_fibre_g`; `"Source of iron"` with no `other.iron_mg` | Otherwise the claim cannot be checked at all. Protein, carbohydrate, sugars, fat and energy are always required, so their claims need nothing extra. |

**XF-08 tolerance.** The factors are the regulation's own: FSS-LD-2020 5(3)(e)(i) lists "(A) Carbohydrates
4 kcal/g ... (D) Protein 4 kcal/g (E) Fat 9 kcal/g". The ±20 % is the regulation's tolerance on declared nutrient
values (5(3)(d): "the tolerance of ± 20 percent of the value for that nutrient declared on the label"). It also
absorbs the 2 kcal/g of dietary fibre (5(3)(e)(i)(H)), which some labels count within carbohydrate and some do
not. The 10 kcal floor stops rounding from failing near-zero products (e.g. 0.5 g carbohydrate declared as
"8 kcal"). A request outside this band almost always has a typo in one of the four numbers.

## 5. Errors and quarantine

### 422 body

```json
{
  "errors": [
    {"loc": "nutrition.added_sugars_g", "message": "Added sugars (10 g) cannot exceed total sugars (9 g).", "code": "XF-04"},
    {"loc": "label.fssai_licence_number", "message": "An FSSAI licence number is 14 digits (spaces allowed); leave it out if the label has none.", "code": "format"}
  ],
  "quarantine_id": "9b2f0c6e1d0c4f1a8a1e5d2b7c3f4a90",
  "correlation_id": "demo-4"
}
```

`FieldError{loc, message, code}`: `loc` is a dotted path to the field (`body` for the whole request).
`message` is for people and may change. Program against `code`, which is stable:

| `code` | Meaning |
|---|---|
| `json_invalid` | The body is not JSON. |
| `type` | Wrong JSON type, or the body is not an object. |
| `missing` | A required field is absent. |
| `unknown_field` | A field the contract does not define. |
| `enum` | Not one of the permitted values. |
| `version` | `schema_version` is not `1.x`. |
| `range` | A number is outside its bounds (§2). |
| `length` | Text too long, blank where required, or too many claims. |
| `format` | Licence number, or a `nutrition.other` key without a unit suffix. |
| `category` | Malformed category id. |
| `XF-01` … `XF-10` | A cross-field rule (§4). |
| `internal` | The gate itself failed. The request is still rejected and quarantined, never accepted. |

### 429 body

`{"detail": "...", "retry_after_s": 2.0, "correlation_id": "..."}` with a `Retry-After` header (whole seconds).
Each `X-Client-Id` has a bucket of `RATE_LIMIT_BURST` requests, refilled at `RATE_LIMIT_PER_MIN` per minute. The
bucket lives in Redis and is shared by every API replica. If Redis is unreachable the limiter lets requests
through and logs it, rather than shutting every client out.

### Quarantine record

Stored in Postgres table `quarantine` (`deploy/postgres/init/20-vihaan-quarantine.sql`; in memory when no
database is configured). It is readable at `GET /v1/quarantine?limit=` and through Grafana:

| Field | |
|---|---|
| `quarantine_id` | 32 hex characters; returned in the 422. |
| `received_at` | UTC timestamp. |
| `client_id` | The `X-Client-Id`. |
| `schema_version` | As sent, if it was a string. |
| `errors` | The same `FieldError` list as the 422. |
| `payload` | The raw body exactly as received (non-JSON bodies wrapped as `{"_unparseable_body": "<first 2000 chars>"}`). |

A quarantined request never has a `runs` row or a queue job (demo #4). Rate-limited requests are not
quarantined.

## 6. Versioning

- `schema_version` is `MAJOR.MINOR`. The gate accepts major `1`.
- **Minor** versions are additive only: new optional fields and new enum members (LLM_Context §6.6). A v1.0
  client keeps working unchanged.
- A **major** version (renaming or removing a field, tightening a rule so that a valid v1 request becomes
  invalid) needs every affected owner's agreement. The gate would then accept both majors during a
  migration window.
- A new cross-field rule is a tightening. It gets the next `XF-` id, is announced to the team, and ids are
  never reused.
- `docs/data-contract.schema.json` is regenerated with `eval/tools/export_schema.py`. Its `--check` mode fails
  when the committed file is out of date.

```json
  "declared_category": "breakfast-cereals",

              "total_surface_area_cm2": 900, "pack_type": "single"},
  "label": {"product_name": "Multigrain flakes", "claims": ["Source of fibre"],
            "ingredients": "Wheat, oats, rice, sugar, salt", "allergen_statement": "Contains: wheat, oats",

```
