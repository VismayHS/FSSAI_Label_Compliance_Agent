## 1. Problem, architecture and platform

Owner: Vismay. Report sections: problem and scope; architecture with deployment boundaries; asynchronous
execution and reliability; cost per 100 runs. Sources: decisions 301–304, `docs/architecture.md`, and the
measurements cited inline.

### Problem and scope
A regulatory affairs analyst checks a packaged-food label before print against two FSSAI regulations that
never refer to each other: Labelling & Display 2020 says what must appear, and Advertising & Claims 2018
sets the conditions a claim must meet. The service returns one finding per requirement, each with
citations to regulation and clause, and a route (`clear-for-print`, `revise-and-recheck`,
`regulatory-review`). It never approves a label. Labels arrive as text; model training, cloud deployment
and images are out of scope.

### Architecture and deployment boundaries
One `docker compose up -d --build` from a clean clone starts eleven services
([decision 304](../decisions/304-vismay-deployment-boundaries.md), diagram in [architecture.md](../architecture.md)):

- **Request path.** `web` (nginx, static build, proxies the API) sends to `api` (FastAPI: gate, 202, polling,
  trace), which enqueues into `redis` (RQ). `worker` × N runs the pipeline and writes to `postgres`
  (runs and steps).
- **Supporting jobs.** `indexer` (one-shot index build), and `stub-llm` (load tests and the breaker demo).
- **Observation.** `prometheus`, `grafana`, `jaeger`, `cadvisor`.

Each boundary has its own scaling, failure and release profile:
- The API scales on HTTP requests and carries no agent code (about 300 MB).
- Workers scale on runs in flight and carry the model and index (about 2.3 GB).
- The index build runs only when the corpus changes.
- The stub keeps load tests from measuring a provider we don't control.

We rejected a single app container, because every replica would carry the model and `--scale` couldn't
isolate run throughput. We also rejected one container per agent: that adds network hops inside one run,
for no measured benefit.

**Rejected or failed requests never start work (D1).** The order on submit is: client id, size limit,
gate (rate limit, validation, quarantine), save as `queued`, enqueue. A reject returns `422` with field
errors and a quarantine id, and no run or job exists. `tools/scripts/smoke.py` checks this on every run.

### Asynchronous execution
`POST /v1/runs` answers `202` with a run id, status URL and trace URL. The client polls with backoff
([decision 301](../decisions/301-vismay-async-polling.md)). Polling won over callbacks for three reasons:
- **Every client can poll.** The browser, Locust, curl and the eval runner can all do it, but a webhook
  needs the caller to run a reachable server.
- **It is stateless on the server.** There are no outbound calls to arbitrary URLs, which would be an
  SSRF risk.
- **It measures D6 directly.** Polling gives the "submission to final result" time the SLI needs.

A webhook stays an extra. Runs go through RQ on Redis
([decision 302](../decisions/302-vismay-queue-rq.md)) to `SimpleWorker` processes:
- **Interchangeable workers.** The payload is plain JSON, everything a run produces goes to Postgres, and
  breaker state lives in Redis, so any worker can take any job.
- **Measured scaling (2026-10-25).** With `--scale worker=3`, three replicas took jobs from one queue, and
  Prometheus discovered all three through DNS with no config change.

**Traceability (D5).** Every response carries a correlation id that is attached to the run, the job, every
step and every JSON log line. The API's submit span travels inside the job payload, so Jaeger shows one
trace from the HTTP request to the worker's run. `GET /v1/runs/{id}/trace` reconstructs a run from the
database alone: the request, every step with its inputs and outputs (queries, full passages, LLM
messages), prompt versions, latency, tokens and cost per step and per agent, queue wait, verdict and route.

### Reliability (A5)
All LLM calls go through `fssai_llm_gateway`:
- **Timeouts.** Every attempt has a timeout, capped by the run's remaining wall-clock budget.
- **Bounded retry.** Only timeouts, connection errors, 429, 5xx and malformed replies are retried, with
  exponential backoff and full jitter. `Retry-After` is honoured, and a retry never goes past the run
  deadline.
- **Circuit breaker.** One breaker per provider, kept in Redis so every worker shares it. It opens after N
  consecutive failures, then fails fast. After a cooldown, one trial call is allowed through: if it
  succeeds the breaker closes, and if it fails the breaker opens again.
- **Degradation.** If a fallback model is configured, the run continues on it and is marked `degraded`.
  Otherwise the gateway raises `ProviderUnavailable`, and the pipeline returns `complete=false` routed to
  `regulatory-review` with the reason. That is an honest error, not a stack trace.

**Demonstrated (2026-10-25, demo #8):** `python -m fssai_llm_gateway.demo` ran in the worker container
against the stub, with breaker state in Redis:
- one healthy call;
- the stub switched off, then three failing calls, each retried once; the breaker opened;
- the next calls failed in 0–1 ms without any HTTP request;
- the stub restored and the 8 s cooldown over, the trial call succeeded and the breaker closed.

**Other failures.**
- A failed enqueue saves the run as `failed` and answers `503`.
- A crash inside the pipeline saves the run as `failed` with its error type.
- `/readyz` refuses readiness in queue mode with an in-memory run store.
- A failed index build no longer stops the stack from booting (incident `2026-10-25-vismay-indexer-py311-worker-crashloop`).

dashboard show cost per 100 runs, cost by step and agent, and the largest single driver, all from the same

and $0.60 per million completion tokens (Groq's model documentation). On the free tier we actually pay $0.

What this does and does not show:
- **The sweep moved the cost, not the total.** Searching every requirement deterministically replaced most `act`
  rounds (23 calls on 26 Oct, 8 now), and the draft now reads passages for every requirement, so its prompt and its
  reply (one finding per requirement) are the largest items.
- **The mean hides the mix.** A run that researches and drafts costs $0.0034–0.0046 (mean $0.0037, so about $0.37 per
  100 such runs). An out-of-scope run stops after the classifier ($0.0002). The two runs that hit the 90 s limit
  stopped before their draft ($0.0010–0.0013). A workload of only in-scope labels sits near $0.37 per 100.
- **Cheaper options, in order of effect:** fewer passage characters in the draft (`RESEARCHER_DRAFT_CHARS`, which

  classifier. The whole eval set (30 scenarios) is measured by the prompt-comparison run pair (Namith, Vihaan).
- **Not a quality result.** All 8 runs ended in `regulatory-review` (safe: none was wrongly cleared). Five escalated

  unsupported. Both causes are on the team's critical path (`docs/contexts/LLM_Context.md` §9).
- On the fakes and the stub every recorded cost is $0, and the report says so instead of inventing a number.

### What did not work, and what we changed
- **The indexer crashed in its container.** The tests ran on Python 3.13 locally, while the containers
  run 3.11. CI now tests on 3.11.
- **One missing setting could stop the whole stack.** A hard Compose dependency on the optional index job
  meant a missing `EMBEDDING_MODEL` stopped the stack from serving at all. The dependency is now optional.
  Both are in the incident log.

## 2. Agent design

Owner: Namith · Requirements: F3, F4, F5, A1, A2, A6, L2, L4, D8 · Status: final; the prompt comparison was measured on 6 Nov 2026 (section 5, decision 103)

### 1. Problem and scope of this part

The section 4.1 case ("source of protein") depends on a provision the request never names. The
labelling regulation (FSS-LD-2020) does not point to the claim condition, which sits in the
Advertising and Claims regulation (FSS-AC-2018). A single retrieval pass returns passages that resemble
the question, so it misses that condition. This part of the system is the reasoning layer that
finds it, and that stops safely when it cannot.

### 2. Topology (A2)

Guardrails (input) -> Classifier -> Researcher <-> Verifier -> Router -> Guardrails (output).
Three agents with different prompts, tools and state, joined only by typed hand-offs
(`LabelCheckRequest`, `Classification`, `ResearchDossier`, `Verdict`). Guardrails, router and the
retry edge are deterministic. Full diagram, per-agent table and the failure table are in
`docs/agent-topology.md`.

| Agent | Tools it chooses | Output |
|---|---|---|
| Classifier | none (rule-based fallback) | category, in-scope flag, detected claims |
| Researcher | `corpus_search`, `clause_lookup`, `request_field_lookup` | dossier: passages, queries, findings, escalation signals |
| Verifier (Vihaan) | `resolve_citation`, `clause_lookup` | accept / retry with hint / escalate |

### 3. The Researcher loop (A1, F4, F5)

`plan` -> `act` <-> `run_tool` -> `coverage` -> `draft`. In `act` the model writes a short
reflection ("does anything I read modify, condition, define or exempt something, and which
regulation holds it?") and then picks a tool or `finish`. This reflection is what leads from a
detected claim to FSS-AC-2018. The `coverage` node is a safety net: every detected claim must have a
search that reached the Claims regulation. On a Verifier `retry` the Researcher keeps its earlier
passages and must change strategy (clause lookup instead of search, the other regulation, narrower queries).

Bounds (A1): 25 steps, 15 tool calls, 90 s wall clock per run, 3 research attempts, all from `.env`.
Tool arguments are checked against an allowlist before a call is made.

Structured output: every reply that must be JSON goes through `ask_structured`: parse, check the shape, and if it is unusable show the model its own reply and what was wrong, once, only if the step budget allows. Outcomes are counted (`valid`, `repaired`, `failed`, `skipped`) and drawn on the agents dashboard. The draft step repairs; the act step does not, because an unusable act reply already falls back to the next suggested search.

Grounding: citation quotes are repaired to verbatim spans of the cited passage or dropped. A finding that
loses all its citations becomes `cannot_determine` with an escalation signal. The agent never uses remembered rules.

### 4. Guardrails (L4)

See decision 101. Input: heuristics over every string in the request (plus folded and base64-decoded
variants), a toxicity lexicon with an optional model, and an optional LLM judge. Output: removes approval
wording, never moves a route toward `clear-for-print`, requires an accepted verdict for it, and drops
citations that do not resolve to this run's trace. Structural defences do not depend on detection: label
text is only ever passed inside data blocks and tool arguments are allowlisted.
Red-team set (`packages/guardrails/tests/attacks.yaml`): 44 attacks, each placed in one field and required to be flagged in that field, and 16 pieces of real label copy that must not be flagged. The attacks cover instruction override, role-play, authority role-play, fake system lines and chat tokens, delimiter escape, base64, leetspeak, zero-width and full-width tricks, six languages, tool-call text and tool JSON, and data exfiltration. CI prints the block rate on every run (`blocked 44/44 (100%); false positives 0/16`) and a test fails if either figure moves. The second round of attacks found five gaps in the first rule set (authority role-play, "no review needed", tool names in prose, tool JSON, exfiltration); each got a rule and a clean-copy fixture so ordinary wording such as "Visit https://..." or "Send your feedback to care@..." stays allowed.
Known gap: an unseen paraphrased instruction passes the heuristics; the judge is the second layer, and the structural defences (data blocks, allowlisted tool arguments, verbatim citations, an output filter that can only lower a route) hold even when detection fails.

### 5. Prompt versions (L2)

Prompts are files under `packages/prompts/fssai_prompts/prompts/<name>/<version>.yaml`, each starting with
`[prompt:<name>@<version>]`, selected by `PROMPT_<NAME>_VERSION`; the version is recorded on every LLM step.

Comparison: researcher 1.0.0 (plain rules) against 1.1.0 (adds an explicit modifier checklist). Both run
on the same evaluation set with the same model.

| Metric | 1.0.0 | 1.1.0 | Difference |
|---|---|---|---|
| Route accuracy | 0.50 | 0.50 | 0 |
| Section 4.1 case reaches FSS-AC-2018 | 1.00 | 1.00 | 0 |
| Mean tool calls per run | 5.38 | 5.62 | +0.25 |
| Groundedness / faithfulness | 1.00 / 1.00 | 1.00 / 1.00 | +0.00 / +0.00 |

Result: no route or safety difference; researcher 1.0.0 got slightly more findings right (finding accuracy 0.46 vs 0.38) with fewer tool calls (5.38 vs 5.62), so 1.0.0 stays the default. Measured on 8 of the 30 scenarios per variant (one key's daily token budget), on the host with BM25-only retrieval, before the whitespace grounding fix that made every clear/revise scenario escalate in both variants, and with the offline judge. Those limits are spelled out in `docs/decisions/103-namith-prompt-comparison.md`; the gaps are within noise.

How the comparison is run: `python -m fssai_agents.compare run` runs the evaluation set once per variant with the researcher and its draft prompt pinned together, paced for the provider's token limit and resumable; `python -m fssai_agents.compare report --write` fills this table and writes the decision record, picking the winner by safety metrics first (unsafe clears, hallucination rate), then correctness, then cost.

### 6. Per-agent metrics and runbook (A6, D8)

Prometheus metrics labelled by `agent`: runs and successes, steps and tool calls per run, per-step and
end-to-end latency, retries; dashboard `infra/observability/grafana/dashboards/agents.json`.
`docs/runbook.md` covers provider rate-limited or down (breaker open) and index missing or stale.
Incident log: `docs/incidents/2026-10-26-namith-diverged-branch-merge.md`.

Demo rehearsal: `python -m fssai_agents.demo --api http://localhost:8000` runs demo 2 (a valid request, every citation checked against the passages in its trace, both regulations cited for a claim label) and demo 7 (an injection in `front_of_pack_text`: flagged field, no LLM or tool step, report that does not echo the attack).

### 7. Decisions and what was rejected

- Reflection inside `act` instead of a separate node: a separate call doubles LLM calls against a shared 25-step budget.
- Heuristics as the default injection detector: free and deterministic; a local model or judge costs a download or a step per run (both kept as options).
- Fixed pipeline with one retrieval pass: rejected, it cannot reach the claim condition.

### 8. What did not work

- A real LLM stopped after two searches and drafted 11 findings, nine of them "no passage was provided"; `coverage` only covered claims, so every label ended in review. Fixed by a deterministic `sweep` that searches every claim condition and labelling requirement first, and by limiting findings to searched requirements (decision 102). One query per requirement did not fit the shared tool-call limit once the verifier ran in every run, so the searches are grouped.
- Giving the model a checklist (prompt 1.1.0) did not make it search more; moving coverage into code did.
- The RDA reference value is not in either regulation, so the 4.1 finding is `cannot_determine` unless the team supplies it (open team question).

## 3. Retrieval and performance

Report section · Owner: Nishkal · Requirements: L1, D2, D5 (metrics, tracing backend, dashboards), D6,
A7 (measurement), D7 (caching), F4 (retrieval side). The design decisions behind it are records 001–004
in `docs/decisions/`.

### 1. Corpus

Two FSSAI compendia, each the principal regulation with every amendment printed next to the text it
replaces:

- Advertising and Claims Regulations 2018, Version-II (16.11.2021), 23 pages.
- Labelling and Display Regulations 2020, Version-VI (22.02.2023), 42 pages.

Both have a full text layer, so no OCR was needed. Provenance is in `data/corpus/manifest.json`: source URL,
the URL the bytes came from, version and sha256. The product category is breakfast cereals (decision
001). Health supplements are out of scope, because Schedule I Note 1 of the Claims regulation sends their
claims to a regulation outside the corpus.

### 2. Chunking and embedding strategy (L1)

**The difficulty (spec §3).** The condition that decides the §4.1 case is a table row in the Claims
regulation: Schedule I, item 11, "Protein · Source · 10% of RDA per 100 g for solids …". The Labelling
regulation, which a label question naturally retrieves, never points to it. On top of that, the
compendium prints superseded and substituted versions of the same provisions one after the other.

**Chunking: by clause, never across one.** A structural parser reads the text layer:

- regulations, numbered in sequence;
- sub-regulations and clauses, as markers accepted only in sequence;
- schedule tables, one unit per row whatever page breaks the row crosses;
- amendment blocks, whose units replace the originals. The originals stay in the index, marked superseded.

A clause that fits in 1200 characters is one chunk; a bigger one is split into its sub-clauses. Each
chunk carries regulation, clause id, heading path (including the schedule's "[See regulation 5 (3) …]"
cross-reference and column names), document version, page and amendment status. A context header, `regulation › heading path ›
clause`, is embedded with the verbatim text; citations quote only the verbatim text. On this corpus:
**425 chunks, 373 in force, all 19 in-force Schedule I rows whole.**

**Embedding.** A small local sentence-transformers model (MiniLM-class, 384 dimensions; the name is in
`EMBEDDING_MODEL` only), L2-normalised, in a LangChain FAISS flat index. Building the index embeds 47
chunks/s on a laptop CPU, about 9 s for the corpus.

**Retrieval** fuses three rankings by reciprocal rank:

- dense similarity;
- BM25 over the same text;
- claim-trigger hints, which map claim wording such as "source" + "protein" to the Schedule I row, 5(3)
  and Schedule II. This is a hint, not a filter.

Superseded text is excluded from search by default. Exact clause lookup (`get_clause`) normalises how a
clause id is written and returns a merged clause or a sub-clause slice, so the agent can follow
cross-references precisely.

**Re-embedding without a rebuild (L1, D2).** Chunk ids are stable passage ids. A table records each
vector's text hash and model, and `--reembed changed` replaces exactly the changed vectors in place. A
rerun on an unchanged corpus rewrites nothing. Freshness (built at, versions, sha256, chunk counts,
throughput) is published as Prometheus metrics by the worker that loads the index.

### 3. Retrieval quality

28 hand-labelled queries (`data/corpus/eval/retrieval_queries.jsonl`), every relevant clause checked against
the PDFs. Run with `python -m fssai_retrieval.evaluate`; real model:

| Config | hit@1 | hit@3 | hit@5 | hit@10 | recall@5 | MRR |
|---|---:|---:|---:|---:|---:|---:|
| dense only | 0.643 | 0.821 | 0.857 | 0.929 | 0.857 | 0.736 |
| BM25 only | 0.679 | 0.821 | 0.857 | 1.000 | 0.857 | 0.776 |
| hybrid | 0.643 | 0.964 | 0.964 | 0.964 | 0.964 | 0.800 |
| **hybrid + claim hints** (default) | 0.679 | 0.964 | **1.000** | 1.000 | **1.000** | **0.823** |

The §4.1 question, in three phrasings: dense search alone puts the claim condition in the top 5 for
**one** of them. Hybrid finds it for all three, with or without hints. This is the spec §5 argument
measured on our own corpus: a request about a label does not resemble the provision that decides it.
Exact terms ("source", "protein", "RDA") carry the match that the embedding misses. Hybrid with hints
missed nothing in the top 5. Dense-only misses in the top 5 were two of the three "source of protein"
phrasings, "high protein claim requirement", and the Schedule II synonyms query ("can 'provides protein'
be used …").

### 4. SLO, measured results and bottleneck (D6, A7)

**Target** (declared before measuring, `infra/loadtest/SLO.md`): complete-run p95 ≤ 60 s at 5 concurrent runs
(one worker, stub LLM with mean 1.5 s and p95 4 s per call), and ≤ 1 % failed runs.

- **Why 60 s:** an analyst's pre-print check against tens of minutes by hand. Long enough for the
  verify-and-retry loop; inside the 90 s run bound.
- **Why 5:** a realistic busy moment for a team of 10–20 analysts.

**Method.** Locust users submit, poll every 0.5 s and report `full_run` from submission to terminal
state. Steps of 1, 2, 5, 10 and 20 users, 5 minutes each, at 1 and 3 workers, cache on and off.

**Results** (full Compose stack in queue mode, every real implementation on, stub LLM; Windows 11, 12
CPUs, Docker 7.6 GB; 5–6 Nov 2026, commit `e224c5a`; raw data and both full tables in
`infra/loadtest/results/`). Cache on:

| Workers | Users | Runs/s | p50 (s) | p95 (s) | Failed | SLO |
|---:|---:|---:|---:|---:|---:|---|
| 1 | 1 | 0.21 | 4.2 | 8.4 | 0 % | met |
| 1 | 5 | 0.24 | 20.0 | **30.0** | 0 % | **met** |
| 1 | 10 | 0.21 | 45.0 | 57.0 | 0 % | met |
| 1 | 20 | 0.20 | 97.0 | 117.0 | 0 % | missed |
| 3 | 5 | 0.63 | 7.4 | 13.0 | 0 % | met |
| 3 | 10 | 0.65 | 15.0 | 21.0 | 0 % | met |
| 3 | 20 | 0.62 | 31.0 | 40.0 | 0 % | met |

- **The SLO is met:** p95 30 s at 5 concurrent runs on one worker, against 60 s, with no failed run in
  any step of either matrix.
- **Failure concurrency:** 20 users on one worker (p95 117 s). On three workers the SLO still holds at
  20 users (40 s), so the failure point is beyond the largest step we ran.
- **Effect of `--scale worker=3`:** throughput ≈ 3× (0.21 → 0.63 runs/s), and at 20 users p95 falls
  from 117 s to 40 s. Workers hold no state, so this needed no code change (A7).

**Bottleneck: queue wait behind one serial worker,** as predicted, now measured rather than assumed. With
one worker, throughput stays at about 0.21 runs/s whatever the load, and p50 grows by roughly one
single-run time (≈ 4.5 s) per user ahead in the queue. One slow run's trace from the 20-user step shows
89.3 s of queue wait against 3.9 s of execution: 96 % of the run was waiting. The 3.9 s itself is almost
all stub-LLM latency (classifier 1.8 s, researcher 2.0 s), and submission stayed under 0.19 s p95, so
neither retrieval, Postgres nor the API is the limit. The lever is the worker count. With a real
provider, the next limit is the free tier's tokens per minute, not our hardware.

### 5. Caching (D7)

Query embeddings and retrieval results are cached in Redis, keyed by model and by index version. A
rebuild therefore invalidates the cache without a flush, and an unreachable Redis degrades to an
in-process cache instead of failing the run. Whole-run and LLM-response caches were rejected: they would
return verdicts made with older prompts or indexes, and would skip the verification the spec grades
(decision 003).

**Measured at the retrieval level** (real model, 28 queries × 5): a search takes 15.7 ms p50 and
18.8 ms p95 uncached, and 0.18 ms and 0.22 ms on a cache hit. That saves about 15 ms per search, or
under 0.2 s per run, against several seconds of model calls. So retrieval caching cuts worker CPU but is
not a p95 lever, and it saves no LLM cost.

**Measured at the run level** (the same load matrix with `CACHE_ENABLED=0`): the change is within noise
and goes both ways. One worker: p95 36 s vs. 30 s cached at 5 users, but 51 vs. 57 s at 10 and 100 vs.
117 s at 20. Three workers: 12 vs. 13 s, 19 vs. 21 s, 36 vs. 40 s. Throughput is the same. Cost per run is
unchanged, because LLM responses are not cached. That is the honest result: the cache is kept for the
worker CPU it saves and for repeat searches inside a run, not as a latency or cost lever.

### 6. Observability (D5)

- `fssai_observability` gives every service JSON-lines logs (with `run_id` and `correlation_id`, and the
  RunContext events flattened to fields), OTel tracing to Jaeger over OTLP/HTTP (a no-op when not
  configured), and trace-context helpers to carry a trace across the queue.
- The stack (`infra/compose/observability.yml`) runs Prometheus, scraping every service including each
  worker replica via DNS discovery, plus Grafana, Jaeger, cAdvisor and Redis/Postgres exporters.
- The *Service overview* dashboard shows run and HTTP p50/p95, error rate, throughput, availability,
  CPU, memory and uptime per container, retrieval latency and cache hit ratio, and index freshness.
- Burn-rate alerts on the SLO are defined in `infra/observability/prometheus/rules/slo.yml`.

### 7. What did not work, or not first time

- **Dense retrieval alone** missed the §4.1 condition for two of three phrasings (section 3).
- **The first chunker** turned "3 g of fat per 100 g" into Schedule I row 3, shifting every later row,
  and read the sentence end "…Schedule – IIA.]" as a new schedule. It was caught by reading the parse
  against the PDF, not by any metric. Recall would have looked fine while every citation pointed at the
  wrong row (incident `2026-10-25-nishkal-chunker-table-rows`).
- **fssai.gov.in reset every connection** from our network, so the corpus came from archived copies of
  the official URLs, with provenance recorded (incident `2026-10-25-nishkal-fssai-site-unreachable`).
- **The model download failed TLS verification** behind antivirus HTTPS interception, while curl worked.
  Fixed locally without weakening verification in code (incident `2026-10-25-nishkal-model-download-tls`).
- **Open: the protein RDA is not in the corpus.** The Schedule I condition is in % of RDA, and both
  regulations defer the RDA to ICMR. Comparing a declared value needs an external, cited reference value
  or an escalation (`docs/eval1/section-4.1-passages.md`).

## 4. Verification and evaluation

Owner: Vihaan · Requirements: F1, F2, F6, F7, A3, D1, D7 (rate limiting), L3, L6 · Status: final. The before/after
numbers were measured on 6 Nov 2026 with the real LLM, from `packages/eval/results/` (decision 205).

### 1. Problem and scope of this part

The system must be trustworthy at both ends. On the way **in**, nothing malformed may reach an agent. On the way
**out**, nothing unverified may reach a person as an answer. The spec says F5 (grounded findings) and F7 (knowing
when not to answer) "hold most of the difficulty", and the glossary sets the priority: *"stating a provision that
does not exist is more serious than declining to answer."* This part also has to *prove* the system's quality,
with an evaluation set and metrics, and keep measuring it after deployment.

### 2. The data contract and the ingestion gate (F1, F2, D1, D7)

The published contract is `docs/data-contract.md`, with a JSON Schema generated from the same code
(`docs/data-contract.schema.json`). The gate (`fssai_gate.gate:RequestGate`) is the single ingestion boundary:

```
X-Client-Id + size (API) -> rate limit -> schema/type + unknown fields -> version, ranges, lengths, formats
                         -> category id -> cross-field rules XF-01..XF-10 -> accept | 422 + quarantine
```

- **All errors at once.** Every stage that can run does. Ranges are checked on raw values, so a type error in
  one field does not hide a range error in another. Each error is `FieldError{loc, message, code}` with a stable
  `code`.
- **Quarantine with evidence.** Each reject is stored with the raw payload, client id, errors and time (Postgres
  table `quarantine`; in memory without a database). It is readable at `GET /v1/quarantine`. A rejected request
  never gets a run row or a queue job, which demo #4 checks by counting runs and the `rejected` counter.
- **Cross-field rules** come from physics or from the regulation itself. Energy must be within ±20 % of
  4/4/9 kcal/g: the factors are FSS-LD-2020 5(3)(e)(i) and the tolerance is 5(3)(d). The others are sugars ≤
  carbohydrate, saturated + trans ≤ fat, mass ≤ 100 g per 100 g, basis vs net-quantity unit, serving pairs, and a
  claimed nutrient being declared.
- **What the gate does not do.** It does not judge compliance (a label with no allergen line is a valid request
  with an `unmet` finding), and it does not reject out-of-corpus categories, which must *escalate* (F7) and so
  need a run.
- **Rate limiting** (D7) is a token bucket per `X-Client-Id` in one Redis Lua script, so all API replicas share it
  atomically and use the Redis clock. It is checked before any validation work, and rate-limited calls are not
  quarantined. If Redis is down it fails open: the queue on the same Redis already answers an honest 503, and
  failing closed would turn a counter-store blip into a total outage.

Decision record 203 lists the options rejected. The gate has 83 tests, including property-based tests (Hypothesis)
that feed arbitrary JSON. They found one real bug, an error with an empty `loc` for a JSON key `""`.

### 3. Verification design (A3, A2)

The verifier (`fssai_verification.verifier:AgentVerifier`) is the second agent: its own prompt
(`verifier_support@1.0.0`), its own tools (`resolve_citation`, `clause_lookup`) and its own per-finding state.
For each finding:

| # | Check | How | Result if it fails |
|---|---|---|---|
| 1 | Citations resolve | The quote must be a substring of a passage retrieved in this run (whitespace, curly quotes and dashes normalised; case kept) | retry, with a hint naming the clause, or the passage that really holds the quote |
| 2 | Numbers | Re-read the claim's condition from the **cited passage** (claim word, threshold, unit, basis per 100 g / ml / kcal) and compare with the declared value, independently of the researcher | `mismatch` → retry; `% of RDA` with no value, bases that disagree, or a value whose ±20 % tolerance band spans the threshold → escalate |
| 3 | Support | One LLM call per attempt (NLI-style): does the passage, with the request facts, entail the finding's status? Only for findings that passed 1 and 2 | retry with "search for the provision that decides …" |
| 4 | Action | Signals or escalate-class problems → escalate; fixable → retry (or escalate on the last attempt); else accept | |

Check 2 exists because of the pitfall that a citation can be real while the conclusion is wrong. In the tests, a
"Source of fibre" finding marked `met` with a perfect quote of *"Product contains at least 3 g of fibre per 100 g"*,
on a panel declaring 1 g, is sent back even when an LLM judge waves it through. Retry hints are specific, and their
strategy changes with the attempt (clause lookup first, then the other regulation), so a retry is never the same
search. `clause_lookup` only sharpens the hint ("the clause exists but was not retrieved"). It never makes a finding
supported, because A3 requires text the researcher retrieved in the run.

**Routing** (`RuleRouter`, decision 201) is an ordered list of nine rules, most cautious first. Each route's reason
starts with its rule id. An unverified verdict, an out-of-corpus category, escalation signals, no findings or any
`cannot_determine` go to `regulatory-review`. So does R6, which encodes the project's core obstacle: **a printed
claim with no finding about it that cites the Claims regulation is never cleared**, and checking one claim does
not clear another. Any `unmet` goes to
`revise-and-recheck` with what to fix; only all-met goes to `clear-for-print`, with the not-an-approval notice.

**§4.1.** The protein condition is *"10% of RDA per 100 g for solids … or 5% of RDA per 100 kcal"* and the RDA value
is not in the corpus. A `met`/`unmet` verdict on it is therefore escalated (check 2: `needs_reference`), and the
reference answers in `docs/eval1/section-4.1-test-values.md` are `regulatory-review` until the team adopts a cited
value. For each case they give the exact range of RDA values under which each basis is met, so the answer can be
read off once a value is chosen.

### 4. Evaluation method (L3)

**Eval set:** `packages/eval/scenarios.jsonl`, 30 scenarios in the breakfast-cereal category:

Groups overlap, because one scenario can carry several tags:

| Group | Scenarios |
|---|---|
| §4.1 variants | 5: pass, fail, synonym, high, basis differs |
| Numeric claims on conditions stated in grams | 10: fibre, sugar, fat and sodium, including a boundary and a basis-differs case |
| Mandatory declarations, veg mark, allergen | 7 |
| Possible small-pack exemptions | 2 |
| Out of scope | 2 |
| Conflicting statements | 3 |
| Claims with no condition | 1 |
| Prompt injection | 2 |
| Traps where one retrieval pass gives the wrong answer | 5, e.g. "Contains protein" as a Schedule II synonym, and a small pack whose exemption is undone by a claim |

Expected routes: 14 `regulatory-review`, 12 `revise-and-recheck`, 4 `clear-for-print`. Each scenario has an
expected route, expected findings and **real supporting quotes**.
`packages/eval/tools/check_scenarios.py` proves each quote is verbatim text of the named clause in the built index, and that
each request passes the gate. It caught one hand-typed quote: the corpus reads "n o sugars" where it was typed as
"no sugars".

**Runner:** `python -m fssai_eval run --tag <name>` runs every scenario through `build("pipeline")` in-process, so
it measures whatever the `IMPL_*` switches select. It writes `packages/eval/results/<tag>.json` with per-scenario rows,
aggregates, the config (no secrets) and the definitions below. `compare` prints a before/after table with deltas;
`gate` fails CI if hallucination or unsafe clears rise, or route accuracy drops.

**Unit:** a *statement* is one finding (requirement, status, explanation).

| Metric | Exactly how it is computed |
|---|---|
| **Groundedness** (TruLens) | Per statement: **0** if any citation does not resolve verbatim to a passage retrieved in this run (or a met/unmet statement cites nothing). Otherwise the judge's support score of the statement against its cited passages, 0–1 (TruLens `groundedness_measure_with_cot_reasons`; the offline judge scores a resolving citation as 1). Per response: the mean over its statements. Reported: the mean over responses that make at least one statement. |
| **Context relevance** (TruLens) | Per retrieved passage (everything any tool returned in the run): relevance to the scenario question, 0–1 (TruLens `context_relevance_with_cot_reasons`; offline: 1 if the passage is one of the scenario's gold supporting clauses, else 0). Per response: the mean over passages. Reported: the mean over responses that retrieved anything. |
| **Faithfulness** | Per decisive statement (met/unmet): **1 if its *status* follows from its cited passages plus the request's declared values**, else 0. Numeric claim conditions are re-derived deterministically; the rest are judged (prompt `judge_status`). Reported: the share over judged statements, with coverage. |
| **Hallucination rate** | Per **response**: true if at least one statement is unsupported (groundedness < 0.5) or unfaithful. Reported: the share of responses that make statements (glossary: per response, not an average). |
| Route accuracy, finding accuracy | Against the expected route; the share of expected (requirement, status) pairs found with that status. Ids are matched exactly, else by same prefix and token overlap ≥ 0.5 (`LBL-VEG-MARK` ~ `LBL-VEG-LOGO`). |
| Escalation recall, unsafe-clear rate | The share of expected-`regulatory-review` scenarios routed there; the share of `clear-for-print` routes that should not have cleared. |

**Why groundedness and faithfulness differ.** Groundedness asks whether the *words* are backed by the cited text.
Faithfulness asks whether the *conclusion* follows from that text and the label's numbers. The fibre example above
is fully grounded (1.0) and unfaithful (0); a unit test pins exactly that case.

**Judges** (decision 204):

- `reference`: offline, deterministic and free; used in CI.
- `llm`: our versioned judge prompts through the gateway.
- `trulens`: the TruLens feedback functions on any OpenAI-compatible provider from env.

All judge calls are cached on disk. RAGAS was rejected: both 0.2 and 0.4 fail to import next to the
`langchain-community` 0.4 that retrieval needs (incident 2026-10-26). The cross-check is judge calibration
instead: agreement and Cohen's kappa against hand labels (`fssai_eval calibrate`).

**Caveats, stated rather than hidden.** Offline numbers are lower bounds on what a reading judge would flag.
Offline context relevance is a gold-clause proxy, not TruLens's reference-free score. With the verifier on, offline
faithfulness shares its numeric parser with the verifier, so the LLM and TruLens judges are the independent
measure.

### 5. Results

**Harness check on the contracts' fakes** (29 scenarios, offline judge). This shows the measurement and the
verifier/router effect, *not* model quality, because the fake researcher only checks the allergen line:

| Metric | Fake verifier + router | AgentVerifier + RuleRouter | Δ |
|---|---|---|---|
| Route accuracy | 0.310 | 0.345 | +0.034 |
| Escalation recall | 0.308 | 0.615 | +0.308 |
| Citation resolution | 1.000 | 1.000 | 0 |

The rise in escalation recall is rule R6: claims the fake researcher never checked against FSS-AC-2018 are no
longer cleared.

**Before/after, one deliberate change** (decision 205: researcher prompt 1.0.0 → 1.1.0, everything else fixed).
Real LLM (Groq), 8 of the 30 scenarios per variant, the same 8 for both, reference judge. The table is produced by
`python -m fssai_eval compare packages/eval/results/researcher-1.0.0.json packages/eval/results/researcher-1.1.0.json`.

| Metric | 1.0.0 | 1.1.0 | Δ |
|---|---|---|---|
| Groundedness | 1.000 | 1.000 | 0 |
| Context relevance | 0.155 | 0.155 | 0 |
| Faithfulness | 1.000 (1 of 29 statements judged) | 1.000 (1 of 42 judged) | 0 |
| Hallucination rate | 0.000 | 0.000 | 0 |
| Route accuracy | 0.500 | 0.500 | 0 |
| Finding accuracy | 0.462 | 0.385 | −0.077 |
| Unsafe clear rate | 0.000 | 0.000 | 0 |

**What it shows.** The deliberate change moved none of the four L3 metrics. Every citation in both variants was a
verbatim span of a retrieved passage (groundedness and citation resolution 1.000), no response stated anything
unsupported, and no label was cleared that should not have been. 1.1.0 got about one finding fewer right, which is
inside the noise of 8 scenarios.

**Limits, stated rather than hidden.**
- *8 scenarios, not 30:* 16 real runs is one free-tier key's daily token budget (200,000 tokens per model per day).
- *Reference judge, not `--judge llm`:* no budget was left for a judge model. The reference judge only decides
  faithfulness for statements it can check without a model, here 1 in each variant, so that row is weak evidence.
  Groundedness, hallucination rate and route accuracy are fully measured.
- *Route accuracy 0.500 measures a bug, not the prompts:* the 4 scenarios expected to clear or to be revised all
  escalated with R1 in both variants, because grounding dropped quotes of words the PDF text splits ("dis played").
  That was fixed straight after (incident `2026-11-06-vismay-grounding-dropped-real-quotes`); the 4 expected
  escalations were all right. Rerun on the whole set after the fix to see the prompts' real effect on routes.

### 6. Feedback and live quality (L6)

- `POST /v1/runs/{id}/feedback {satisfactory, reason}` stores feedback with the run's route at that moment, in
  Postgres table `feedback`. It returns 404 for an unknown run and 409 for an unfinished one.
- `GET /v1/feedback/summary?days=` gives the satisfactory rate overall, by route and by day, and the top reasons
  (normalised text).
- `python -m fssai_eval live --sample 10` scores the newest completed runs with the same metrics (the
  reference-free ones; there is no gold answer live) into `quality_scores`, once per run and scorer version. The
  opt-in Compose service `eval-scorer` runs it every `LIVE_SCORE_EVERY_S`.
- Grafana "Quality and trust" (`quality.json`) charts live groundedness, faithfulness and hallucination over time,
  the feedback rate by route and day with the top reasons, and the gate's accepted, rejected and rate-limited flow
  with quarantine by error code.
- `python -m fssai_eval candidates` turns unsatisfactory feedback into **draft** scenarios, tagged `needs-review`.
  A person sets the expected answer before one joins the eval set; nothing is added automatically, because an
  unreviewed "expected answer" would be invented.

### 7. What did not work, and what was rejected

- RAGAS as a dependency (dependency conflict; section 4).
- A borderline band measured from the *threshold*. It was replaced by the regulation's own rule: the ±20 %
  tolerance applies to the *declared* value (FSS-LD-2020 5(3)(d)), so a value is uncertain exactly when
  declared × (1 ± 20 %) spans the threshold.
- An absolute "no unsafe clears" rule in the CI gate. It would fail on today's fakes forever, so it is relative to
  the baseline, like the other rules.
- Recording `resolve_citation` as a tool step. It touches no corpus, and doing so would spend the run's tool-call
  budget (A1), so its calls are listed inside the verification step.
